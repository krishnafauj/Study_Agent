How a document gets parsed

A PDF is never parsed as a whole. Upload only stores the file; each page-range section is parsed on its own — extract → chunk → structure → embed → save — so a big book never hits the LLM in one shot.

1

Upload  POST /api/files/upload

Multer takes the PDF (100 MB, PDF-only). A SHA-256 hash dedupes re-uploads; page 1 text derives a friendly filename; the bytes go to S3 and a UserFile is created. Page count is stored — no parse, no LLM.

2

Create a section  POST /api/access/:fileId/sections

You define a page range. A PermissionSection is created with parseStatus: "parsing", the request returns immediately, and parseSection() is fired in the background — parsing is triggered the moment a section exists.

3

Parse that section  sectionParseService.js

Fetch the PDF from S3, clear any old topics for the section, then run processPageRange over just its pages — the five-step flow in the diagram above (extract → chunk → LLM → embed). Progress ticks on the section itself.

4

Save topics

The outline (chapter → topic → subtopic) and the leaf chunks are written as Topic documents, each stamped with sectionId and real page numbers. The section flips to parsed with a topic count, and the UI badge updates from “Parsing %” to “✓ N topics”.

5

Build the knowledge graph  optional · one click

buildConceptEdges derives prerequisite links across the parsed topics — earlier concepts a later topic depends on — stored as ConceptEdge documents. Built once by keyword matching, read cheaply at chat time.

6

Answer, in scope  chat-stream

A chat bound to a section retrieves only that section's pages, semantic-ranked over the chunk embeddings. Depth-1 prerequisites from the graph lend a definition from an earlier, locked section — never its full text. That is the “don't overcross” guarantee.

One thing to get right: page ranges are 1-based PDF page numbers, not the printed page labels inside the book. If they don't line up, the extracted range is off by the book's front-matter offset.
